# AI分解の結果はフラットな Task として生成する

タスクを AI が複数の実行可能な単位に分割する「分解」機能を追加するにあたり、生成された Task 群を親子関係で保存するか、独立した Task として保存するかを検討し、後者を採用した。

## 背景

Issue #148 §2.2 は「サブタスク」を明示的に非スコープとしており、`tasks` テーブルは元々フラットな構造で、Now の 0/1 件保証・Estimate 集計・`deck_order` などの不変条件はすべて「Task に階層がない」ことを前提に組まれている。分解機能をこの上に素直に足すなら、階層を持たせるか持たせないかがまず決まる必要があった。

## 理由

- 親子関係を持たせると、親 Task の Estimate をどう扱うか（子の合計か、独立値か）、Now は親と子のどちらを指せるか、`deck_order` は親単位か子単位か、といった既存不変条件への波及が大きい。
- 分解の目的は「大きすぎるタスクを1ポモドーロで終わる単位に割る」ことであり、割った後の各 Task は完全に独立して着手・完了できればよい。親を残す必然性がない。
- 元の Task（分解前の大きいタスク）は分解確定時に削除し、生成された Task 群に置き換える。元 Task が Now を指していた場合は、生成された Task 群の先頭を自動で Now に昇格する（[[0006-derived-task-state]] の「削除時は `current_task_id` を NULL にする」規則の上に、分解確定時だけ例外的に再昇格を行う）。

## 結果

- `tasks` テーブルに親子関係を表すカラムは追加しない。
- 分解で生成された Task は、元 Task の `planned_for`（Today/Backlog）をそのまま引き継ぐ通常の Task として insert される。
- 分解確定前の AI 生成結果（編集・削除・並び替え可能な未確定状態）は `Task` ではなく別概念として扱う。`CONTEXT.md` の「分解案」を参照。
